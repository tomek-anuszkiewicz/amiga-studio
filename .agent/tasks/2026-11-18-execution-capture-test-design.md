# Practical test design for execution capture

Task `WORKFLOW-EXECUTION-CAPTURE-20261117`. Starting code `ba273734ee86f36012e6bc90c355345822c26f28`. Acceptance follows sections 2 through 10 of the [approved plan](2026-11-17-workflow-execution-capture.md). The following are planned observations. The earlier rollout sample in section 4 found patch bodies and a matching thread ID. It did not exercise collection, a live receiver or the selected CLI version. The existing workflow result validator checks paired reports and referenced file hashes.

## Trial setup

Use one small real task in a dedicated, persistent Codex CLI conversation. Give it a harmless text fixture, a generated non-secret attachment with known bytes and a short assignment with unique action markers. Use a disposable independent local Git repository with a primary checkout, a linked worktree and disposable refs for the lifecycle trial. Run the selected collector and CLI configuration only for this trial. Bootstrap through direct commands where tools do not yet exist. Exercise the implemented operations at their normal entry points when available.

Before covered work, record the selected turns, known file contents and hashes, expected edits, trial markers and exclusions on a private observer sheet outside the archive. Keep the expected IDs of excluded threads and marker literals out of task prompts, commands captured inside the trial and expected archive contents. Use synthetic unregistered events or a dedicated second test conversation. Use an existing shared IDE only if specifically selected and its current export and join can be demonstrated safely. Stop for a user decision if an IDE change is necessary. Keep process-local CLI settings isolated from active editor sessions and record their effective non-secret values.

## S1. Read the approved inputs back from Git

Before implementation, record the base, working tree/index status and selected inputs, including any dirty or untracked dependency. Retain the approved plan, design, decisions, acceptance criteria, attachment bytes and environment inventory in the initial local commit. Identify the governing workflow and any candidate definitions separately. Use native Git object reads at `start_commit` to compare bytes against the approved copies. Verify the selected paths and absence of unrelated data, raw sessions and credentials. Record the new SHA after commit creation.

Compare inventory values with direct read-only probes of the selected executables, installed packages, lockfiles and configured role settings. Cover the host, Rust/native tools, Python, Node, Docker and role/client/plugin settings where relevant. Record failed or unavailable probes and preserve declared versus installed values. For comparison, retain two inventories. A controlled copy can vary one version, remove an entry and mark another probe unavailable. Expect distinct changed, missing and unknown observations and intact source inventories. Record which comparison inputs were controlled and which were measured in the actual execution.

## S2. Admit only the selected range to the receiver

Obtain the dedicated thread ID during setup and join it to the persisted session header. Record the real CLI version, registration acknowledgment/readiness, execution ID, task ID, Git common directory and exact selected start and stop. Exercise registration from the primary and linked checkouts and reject a different repository. Use a control turn before the start, a covered turn and a later turn outside the end. Check any explicitly selected continuation and one known child against independent runtime linkage. Keep an unselected continuation outside. Compare the user's intended range with selected raw records even when a thread resumes.

Use the upstream Collector, a loopback intake and a fixed YAML filter first. Confirm service identity, actual effective filter and readiness before starting the covered turn. Observe the same receiver across eligible registrations, the concrete failure on a probe endpoint already held by a harmless process, and flush and shutdown after active ranges close. Exercise mixed harmless records carrying an allowed ID, an unrelated ID and a missing ID. Inspect every output segment. Expect only allowed in-range evidence, including at least one identifiable record from the real turn. Generated events establish filter behavior only. Use separate attribute checks for logs, spans and metrics. Omit a signal from archival when attribution cannot be established. Do not spool unfiltered intake. Check the durable output for excluded markers and correlate every retained record with an admitted execution. Retain source and boundary locators for the included records.

A fixed ID filter alone cannot isolate earlier or later turns in a reused thread. For the fixed pilot, bound intake with the dedicated launch and verified time range. If isolation cannot be enforced before writing, stop that path. Exercise a dynamic intermediary only if the pilot demonstrates a need. In that case, use a mixed batch, an acknowledged registration, two overlapping executions and a child initially lacking verified lineage. Check that only verified descendants and explicitly selected continuations enter the appropriate archive. Close one execution, restart the intermediary and send a delayed covered event and an out-of-range event. Check event boundaries, persisted registration, continued admission for the active execution and reported loss when lineage remains unresolved. Compare normalized accepted record content and attached attributes with the known payloads.

## S3. Follow one real turn and one worker handoff

Save the CLI JSON stream and selected rollout records. Request a recognizable intermediate and final reply, a child assignment and returned payload, a real tool invocation, a harmless failing command followed by success, and one bounded wait with a stated reason. Retain actual authorizations, stage/round identities, termination, commands, arguments, temporary script bytes, exit statuses and complete reports for the checks and reviews actually performed. Compare the observer's known messages and command outcomes with thread, turn and call locators. For console truncation, compare the excerpt with the independent full report. Locate the final response from a later invocation when the end boundary includes that response. Preserve failed/interrupted outcomes at their observed boundary.

Compare available source timestamps, wait intervals, retries, parent/child overlap, model/effort per turn and scoped usage counters. Preserve cached/reasoning fields when exposed and label cumulative and per-call counters according to their source. Distinguish the configured role settings, runtime observations and any missing runtime field. Compare OTLP with native records for detected skill use, actual procedure evidence, API attempts and elapsed times, MCP timing/errors and other attributable fields. A skill file read or a declared invocation has its own evidentiary value. Report what each source adds, with raw time, ID, segment and record locators. Never infer hidden reasoning, cost, a retry or total elapsed time from summed child durations.

## S4. Reconstruct the known file changes

Prepare a tracked file containing `base`. In a named stage apply a patch changing it to `patched`. In a second stage use a shell script to create another file with known bytes. In that stage write a transient marker and restore its original bytes before stage completion. Compare independent fixture bytes before/after each action and at stage ends with rollout patch bodies, CLI change notifications, tool commands/results and any stage-scoped Git evidence. Record paths, content and granularity for additions, renames, deletions or binary attachments actually used. Attribute edits by stage, actor, turn and call where the evidence allows. A correct final tree contains the persistent edits and lacks the transient marker. A complete claim about the reversal also needs evidence of the intermediate change and restoration. Report missing bodies, ambiguous ownership and net-only evidence explicitly. Keep intermediate fixture checks in the trial evidence, outside the captured system's source of truth.

## S5. Seal, inspect and recover the evidence

Check the archive ignore rule before its first write. Collect under the surviving primary checkout using the selected end boundary. Compare dedicated rollout contents and CLI bytes with originals. For a thread with excluded turns, compare only admitted raw records and their source ranges. Account for every segment and required non-Git file, including attachments, selected telemetry, reports and scripts. Independently enumerate relative paths, byte counts and SHA-256 hashes and compare them to the manifest. Check task/execution IDs, format/tool versions, source/workflow and final Git identities, outcome, lineage and last included event. Compare each required source against the observer sheet; a self-consistent manifest can still omit a source.

Exercise a temporarily incomplete JSONL tail using a controlled copy, preserve provisional status and finish collection after the producer completes. Expect an additional archive revision with the earlier evidence intact. On a disposable copy of the archive, change one byte and omit one expected segment. Expect concrete integrity and completeness findings in the paired report. Verify that collection preserves the original source files. Record whether an independent backup actually exists. In the disposable Git repository only, inspect reachable history for a separate starting commit and one consolidated implementation commit where applicable. After trial worktree retirement use the surviving checkout to retrieve the input blobs, archive and final tree. On the real project, verify reachability and local history without removing a worktree or publishing trial refs.

## Completeness decision

Produce one text/JSON result for the eight required information rows. S1 checks starting inputs. S2 checks registration and lineage. S3 checks communication, tools and skills, timing and progress, and usage and verification. S4 checks change history. S5 checks integrity and survival. For each row record an observed example or missing expected marker, source and locator, status (`present`, `partial`, `missing`, `unavailable` or `not_exercised`), and what OTLP contributed. Identify the checked version, surface and range. Record software verification and review outcomes independently, including actual canonical evidence at its authorized trigger.

Stop for a material gap, archive contamination or a need to reconfigure the IDE and present the concrete evidence for decision. The trial determines which signals merit routine use and whether dynamic filtering is justified. Rerun only an affected segment after an authorized correction. Retain the prior evidence and verdict.
