# Official skill recommendation matrix

Generated by `python tools/workflow/result.py --matrix`. Edit the
[authoritative matrix](../tools/workflow/skill-matrix.json), then regenerate this view.
The [receiving procedure](../.agents/references/workflow-guidance.md) owns its use.

Rows are the skill that returned a result; columns are possible next skills.
A cell names conditions to consider, not mandatory execution or permission.
Multiple codes are alternatives. An empty cell (`-`) means no official recommendation
for that pair. It does not prohibit the user from directly selecting that skill.
Normal authorization, prerequisites, role boundaries and verification still apply.

The receiver chooses normally one to three relevant options, explains the evidence
for each selected condition, and waits for the user's choice. Completion, clarification,
approval, stop and defer need no invented skill or matrix cell. Reuse valid results;
do not repeat checks or continue completed work merely because a cell exists.

## Cell conditions

| Code | Required context |
| --- | --- |
| RTY | The same operation remains unfinished, failed or interrupted, and resolved missing input or a concrete changed approach justifies another bounded attempt. Preserve its predecessor, cumulative rounds, limits and partial effects. An exhausted invocation needs a newly authorized continuation; never reset its budget or repeat successful work. |
| PLN | An identified change within the current task needs an initial plan or a substantive revision because new evidence exposes a requirement, scope or acceptance decision. Preserve unresolved decisions for the user; do not invent another task after completion. |
| TST | Approved requirements or an accepted change plan need meaningful test scenarios, or an interpreted finding identifies a new behavioral scenario within the current scope. Raw coverage percentages alone do not establish this need; preserve independent expectations and protected criteria. |
| IMP | An approved change plan and test scenarios, or equivalent explicit requirements, identify unfinished implementation in the current task. Required decisions and inputs are resolved, and the proposed write scope includes the agreed code and tests with their focused checks. |
| FIX | Concrete, stable finding IDs and evidence identify a repair within the current task. The proposed option names the findings, current candidate, approved expectations and focused reproduction or regression checks. New scenarios, changed requirements and weakened tests or golden references require their separate decisions. |
| OPT | An actual profile identifies a specific optimization candidate and mechanism worth evaluating. The option names its candidate IDs, original comparable baseline, workload, approved behavior and correctness checks; implementation and measurement stay within that selected scope. |
| PSH | The approved task specifically requires an unfinished PowerShell change with defined invocation behavior, write scope and meaningful validation scenarios. Use the script-specific implementation skill only for that identified work. |
| AUD | Supplied tests, execution or coverage evidence needs interpretation against approved behavior before deciding whether a defect or missing scenario warrants changes. Keep measured gaps, assertion quality and unmeasured areas distinct; do not infer new tests from a percentage alone. |
| COV | Changed production code or an explicit measurement request triggers coverage assessment for a named candidate and scope, and applicable evidence is missing or invalidated. Preserve the existing coverage tool, collection boundary and measurement authority; do not remeasure unchanged successful evidence. |
| REV | A named independent review lane is required for an actual stable candidate and its approval is missing, invalidated or needs reassessment after relevant corrections. Supply the exact candidate and lane scope with fresh context; retain applicable evidence from unaffected lanes. One approval never establishes overall readiness. |
| SPC | The current batch or explicitly selected change needs scoped specification compliance review, and applicable evidence for its exact candidate and tracked paths is missing or invalidated. Supply approved requirements and review compatible documentation knowledge without accepting an implementation conflict as a new requirement. |
| PAR | An actual milestone, combined integration assessment or explicitly selected subsystem review requires semantic parity analysis, and applicable evidence is missing or invalidated. Supply the complete required scope and approved sources; a narrow result cannot substitute for a broader required assessment. |
| LNK | Selected documentation changes or an applicable gate require a metadata and link audit whose evidence is missing or invalidated. Keep the required vault scope and reference-book approval boundaries; the audit reports repairs rather than authorizing them. |
| MAN | A concrete hardware question blocks or qualifies the current scoped work and authoritative manual evidence is still needed. Supply the question and relevant sources; keep hardware requirements separate from implementation behavior and hypotheses. |
| MOD | A concrete question within the current task needs evidence from an identified reference model and revision after considering available manual evidence. Supply the unresolved question and source scope; model behavior remains model evidence, not proof of hardware behavior. |
| OBS | A concrete hardware claim in the current task needs original physical measurement evidence. Supply the signal or behavior question and available provenance; do not substitute software output for observations or invent a measurement source. |
| CPU | A selected CPU vector, case or trace exposes an unresolved CPU discrepancy with sufficient reproduction evidence for diagnosis. Preserve state, clocks and timed-transaction distinctions; diagnosis does not authorize implementation, changed expectations or a broader vector run. |
| NEW | An approved selected plan needs its explicitly chosen new task checkout. The source, destination and physical asset scope are known; creating the checkout does not select implementation or authorize a different task. |
| AST | The existing selected worktree has identified missing local assets, configuration or graph seeds. The exact repair paths, validated source and repair authority are available; do not replace unrelated configuration or merge Git histories. |
| SYN | The selected task candidate actually needs synchronization with a recorded immutable local master commit, including recovery from a changed publication base. The target checkout, source identities and merge authority are explicit; publication failure alone does not authorize synchronization. |
| MRG | The selected synchronization left an actual pending merge with identified conflicts. The merge identity, selected paths, approved requirements and existing completion authority are available; a clean merge is not a reason to invoke conflict resolution. |
| DOC | Known documentation findings or necessary compatible updates identify exact documents and write scope within the current task. Supply approved requirements and evidence; resolve specification conflicts and any required reference-book metadata approval before editing. |
| DIA | An actual closure trigger or explicit compaction request requires consolidation of identified settled diary history. Supplied completion evidence distinguishes settled from unfinished work; preserve unique knowledge and keep all changes before the final candidate is accepted. |
| PRN | An actual closure request identifies exact completed roadmap items supported by implementation, semantic and verification evidence. Preserve unfinished scope and checkpoints; pruning remains provisional until the required final gates, diary work and closure commit succeed. |
| BAT | The current task has an explicitly selected batch scope and candidate whose partition, messages, diary or readiness record needs preparation or updating after material changes or new evidence. Preserve existing index entries and staging authority; preparation may report missing gates without obtaining them. |
| CMT | Commit authority covers an exact prepared candidate, partition, messages and diary or closure content. All four independent review lanes approve that candidate, canonical verification and every applicable milestone or other gate pass, and no unresolved blocker remains. Freeze and create only the authorized mechanical commits. |
| PUB | The selected task has accepted, sealed source and target identities with the required committed closure record, and exact publication authority is available. The recorded base and candidate remain current; use only the existing eligible publication protocol, without inferring push or cleanup authority. |
| CLN | Publication is confirmed and closure is committed for the exact selected task. Cleanup authority names its plan, branch and worktree, and preservation checks are satisfied. Cleanup does not republish, recreate commits or discard unrelated work. |
| CHK | A named focused check is required for the current candidate and has not completed, or relevant changes or resolved failure causes invalidate prior evidence. Supply the exact command, environment and boundary; do not repeat applicable success or expand into a broader suite. |
| VER | An actual batch needs canonical commit-profile verification for its stable complete candidate and recorded baseline. Evidence is missing, invalidated or a failed cause has been addressed. Retain applicable successful groups and the existing results directory; a passing focused check is not canonical evidence. |
| MIL | An actual milestone requires the canonical milestone profile for its complete stable candidate. Evidence is missing, invalidated or a failed cause has been addressed; preserve the required full scope. A passing profile alone does not establish milestone closure. |
| QRY | A specific unanswered relationship question in the current task can be checked in an identified existing graph. The graph, source scope and query are known; the operation remains read-only and confirms relevant definitions directly. |
| PTH | The current task has a concrete relationship question between known, source-qualified endpoints in an identified existing graph. A path or no-path result would resolve that question; do not create a new investigation merely because graph access is available. |
| SYM | Understanding a known symbol and its relationships is necessary for the current scoped task. The symbol, graph and source snapshot are identified; read the owning definitions and do not broaden the requested analysis. |
| GRF | A specifically identified missing or stale graph blocks the current task, or an explicit refresh request names it. The selected project or reference source, root and refresh authority are available; refresh only that graph and do not infer semantic extraction. |
| SEM | Explicitly selected project documents need their semantic relationships extracted into the project graph. The source scope, graph state and write authority are available; structural refresh and document editing alone do not authorize this separate operation. |
| IMG | The current GUI task needs new image evidence from an identified existing capture scenario and output location. State the capture boundary; a saved image alone is not an interpreted diagnosis, accepted visual result or repair instruction. |
| IDX | Accepted documents within an explicitly selected supported source scope need shared RAG indexing, and publication authority, configuration and retrieval probe are available. Document editing, graph changes and audit completion alone do not authorize indexing. |
| PRF | An unresolved performance question within the current task needs actual profiling of a named boundary and workload, and measurement is authorized. Collect comparable evidence before proposing implementation; do not start another optimization because prior work completed. |
| SKILL | The approved workflow change needs one unfinished atomic operation with a defined result and an existing executor. Name the operation and its authorized definition and registration paths. |
| ROLE | The approved workflow change needs one unfinished named role with a distinct responsibility, context or write boundary. Name that boundary and its authorized definition and registration paths. |
| ENV | An adopted task needs its starting environment recorded before its input commit. |
| CMP | A saved baseline and a separately captured inventory are available for the selected comparison. |
| REG | The user has selected a thread, repository and execution boundary for capture. |
| COL | A recorded execution has a closed boundary and its evidence is ready for collection. |
| REC | A new archive revision and independent expected observations are available for assessment. |
