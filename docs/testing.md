# How the Emulator Is Verified

Use this guide to understand what each test checks, interpret a result or start
investigating a failure. The verifier's command-line help and the verification
reference describe the exact commands and how they select checks.
[tools/verification/README.md](../tools/verification/README.md)

## Different Tests Answer Different Questions

The emulator has to produce the right state at the right time. If a bus access
happens in the wrong clock phase, the instruction can still finish with the
expected value. Each kind of verification answers a different question.

| Evidence | Question it helps answer |
| --- | --- |
| Crate tests | Does an individual component behave as expected? |
| Integration tests | Do the CPU, bus, machine loop and peripherals coordinate correctly? |
| 68000 SingleStep vectors | Does an instruction match generated final state, instruction clocks and the timed bus callback sequence? |
| CPU wait-state crate tests | Does the CPU retain and retry a refused transfer correctly? |
| Whole-machine captures | Does a selected hardware program produce the expected visible result? |
| Performance measurements | How much host time does an emulated workload consume? |

Architecture and quality checks enforce project constraints. Establishing
hardware timing requires timing evidence as well.

## CPU Accuracy and Bus Waiting

The CPU harness uses Tom Harte's SingleStepTests, a large collection of
instruction cases generated by a software implementation. For every vector it
runs, the harness compares registers, instruction clocks and timed bus callbacks
with the JSON reference. A sampled run selects fewer inputs and makes the full
comparison for each selected case. SingleStep interprets registers and bus data
according to the published JSON format. Test names serve as descriptions only.
Internal delays advance the expected transaction timeline, so the harness can
detect an early or late read or write even when the total clocks match. The CPU
verification specification lists the state compared and the signal limits of the
callback interface.
[CPU verification specification](../Obsidian/Amiga/Design/Verification/CPU%20SingleStepTests.md#12-input-scope-and-complete-verification)

SingleStep uses the [reviewed SingleStep override catalog](../crates/test_runner/tests/overrides/singlestep/README.md)
for approved corrections to exact records, with the originals retained in `ref_src`.

The ordinary CPU crate suite includes tests that use PhysicalMemory and a small
recording wrapper. The wrapper lets specific transfers through immediately or
after one or more refusals. The tests check CCK phases, verify that every retry
refers to the same transfer, count exactly one success and check the wait cost
against an independent count of refusals. Focused cases cover the halves of long
transfers, address updates, prefetch, stack and exception paths,
read-modify-write and MOVEM/MOVEP progress.
Production Agnus arbitration and the complete chipset scheduler require
integration tests. The memory-placement and DMA-schedule permutation tests have
been removed.

For source and procedure details, start with [test_runner](../crates/test_runner/)
and the [verification command reference](../tools/verification/README.md).

## Whole-Machine Behavior and Performance

External hardware programs and reference captures show the combined effect of
instruction timing, DMA, video and peripherals. You can use the available
vAmigaTS reference captures to investigate behavior. The previous capture runner
was removed and no executable entry point currently compares captures. The
roadmap tracks the work needed to restore whole-machine capture verification.
[External hardware verification work](../ROADMAP.md#external-hardware-verification)

Benchmarks measure host execution time. Cycle assertions measure emulated time.
Use stored benchmark results as a comparison reference and explicitly run a
measurement to get current results. The benchmark regression test targets and
the old chipset throughput runner have been removed. The benchmark design
explains what the current measurements capture.
[Benchmark design](../Obsidian/Amiga/Design/Performance/CPU%20Instruction%20Benchmarking.md)

## Run Verification and Read the Result

During batch preparation, run this command from the repository root.

```powershell
python tools/verification/verify.py commit
```

The verifier keeps the full quality checks and selects Rust tests for changed
packages and packages that depend on them directly or indirectly. It skips Rust
tests for independent documentation and known Python tools. Shared build inputs
and changes with unknown impact require full verification. Use `commit --plan`
to see the selection. The verifier reads the working tree, including unchanged
files when a check needs them. It works without staging and leaves commit
creation to a separate action.

Ordinary task completion uses the relevant focused checks. Run full SingleStep
verification through the selected milestone profile or explicitly for diagnosis.
Changes alone do not select it in the commit profile. Language scans and Git
operations are selected separately. Selecting ordinary CPU tests also runs the
CPU waiting tests. Use `python tools/verification/verify.py --help` to see the
available profiles. For execution details, see
[tools/verification/README.md](../tools/verification/README.md#completion-verification).

An ordinary crate test report includes coverage for the selected packages and
current source files. A report for part of the workspace applies to that part
only. Coverage shows which code ran. Assessing the assertions, the hardware
cases represented and execution speed needs other evidence.

For an identified diagnostic need or an explicit request,
`python tools/verification/verify.py test coverage crate NAME` produces a detailed
report without completion gates. Measure coverage and review gaps when selected
for the change. Use the source locations the report marks as unexecuted to
identify and test missing behavior.
[Coverage workflow](../tools/verification/README.md#coverage-guided-testing)

The repository launchers print a case report kept in the primary checkout. Use
it to find native diagnostics, tell which groups ran fresh or were reused, and
read durations when available.
[Case-report reference and launchers](../tools/verification/README.md#case-reports)

To assess the result, check which suites ran, whether they used full or sampled
inputs, and whether a failure or missing asset limited the run. A pass covers
the cases and assertions that ran. When you repeat batch verification, it can
reuse successful groups whose inputs still match and whose evidence is intact.
The official verdict still requires every final gate. The evidence applies only
to the candidate as verified, with its changes taken together. The testing
specification covers the broader design and verification strategy.
[Testing specification](../Obsidian/Amiga/Design/Verification/Testing%20Strategy%20and%20Quality%20Assurance.md)
