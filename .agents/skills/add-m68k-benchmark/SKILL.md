# Add an M68000 instruction benchmark

Use existing [CPU performance test cases](../../../benchmarks/m68k/) as working examples, not fixed templates. The [benchmark README](../../../benchmarks/m68k/README.md) describes the catalog and command; the [shared runner](../../../benchmarks/m68k/runner.rs) owns assembly, fixture preparation, execution checks, and measurement. This catalog is the active CPU measurement workload; the retained decoder-derived baseline is incompatible with it. These cases measure only the host cost of running a complete CPU program in Fast RAM; they do not test opcode correctness or measure the whole Amiga. Choose separate cases for distinct execution work or performance cost, not solely to cover different results, condition flags, signs, or register aliases. Correctness belongs to the CPU test suites.

## Define the case

1. Identify the instruction form, addressing mode, register banks, memory effects, and control path to measure. Include A7 when its stack behavior changes the path; other register aliases need a separate case only when their behavior differs. Give the case a descriptive directory under `benchmarks/m68k/<instruction-family>/<case-id>/`. State which executed instructions are targets and which are setup or control instructions. Do not call total guest instructions a target count when helpers are present.
   Before writing the case, inspect an existing `program.s` and `case.json` with the same addressing mode and operand role, preferably for a similar instruction. Use its assembly layout, fixture setup, and reset strategy as a starting point. Recheck operand sizes and values, register changes, memory bounds, reset frequency, and executed target count for the new instruction.
   Read the current opcode implementation, including effective-address handling, cycle calculation, memory access, and exception paths. Map operand and CPU-state conditions to distinct execution work or timing, and check those paths against the instruction specification. Choose operands that exercise each performance-relevant path; keep unrelated inputs and helper work equivalent when comparing cases. An implementation branch alone does not justify a separate case if it does not change the work or cost.
   Where applicable, include taken and untaken conditional branches, loop termination, valid and overflowing arithmetic, divide by zero, traps and other exceptions, privilege failures, and interrupt entry only when these paths execute different work or have different cost. Do not benchmark Address Error (vector 3) caused by odd addresses; keep instruction fetches and word/long data accesses aligned. Keep externally triggered interrupts separate from exceptions raised by an instruction. Do not add cases merely to check flags, sign extension, final values, or other correctness properties.
   Choose representative D0-D7 and A0-A6 registers with a reproducible, reasonably varied selection across cases; record their required starting values in the initial state. Do not always default to D0/D1 and A0. Keep operand, destination, and index registers distinct where their roles require it. Select A7 only for an intentional stack-pointer case: document whether USP or SSP is active, initialize that bank explicitly, and check the stack bounds and byte postincrement/predecrement rules. Do not include A7 in an ordinary random register draw.
   Choose nontrivial fixed arithmetic operands for ADD, SUB, MUL, DIV, and other measured operations. Do not hand-pick `1` or an exact power of two (`2`, `4`, `8`, and so on) as an arithmetic operand in `case.json`, static data, or a setup instruction. Prefer values with several set bits and verify that they keep the intended performance path, such as a normal quotient rather than overflow or divide by zero. Generated random data may contain any word, including zero and powers of two. Apply this rule to chosen operand values, not addresses, addressing displacements, masks, or benchmark control counts.
   Structure every case around a four-target sequence inside `rept`: execute the measured instruction four times, with a helper after each target. For Bcc, use `MOVE.W #imm,CCR` as that helper. For Scc, use the usual `MOVE.L Dn,Dm` helper with a nonzero source so its flags remain suitable for the intended byte result. For DBcc, reload the counter with `MOVE.L` after each target and then set the flags with `MOVE.W #imm,CCR`; the reload is required for repeated decrement paths. For Bcc and DBcc, choose the immediate condition bits for the named taken, untaken, condition-true, branch, or counter-expired path. Scc never branches; check that the `MOVE.L` helper leaves flags selecting the intended `$FF` or `$00` destination byte. Ensure the first target sees the intended condition bits through `initial_sr` or the default SR, and verify all four targets and subsequent repetitions. Recalculate Bcc and DBcc branch destinations after changing helper sizes. Use [ADD.W D1,(A0)+](../../../benchmarks/m68k/add/add_w_d1_postincrement/program.s) and [ADD.W A2,D5](../../../benchmarks/m68k/add/add_w_a2_d5/program.s) as the `MOVE.L Dn,Dm` patterns for other instructions. In the first, `MOVE.L` is a deliberately inert helper for a target that advances through independent memory words. In the second, each `MOVE.L` restores a destination register before the next `ADD`. Choose source and destination registers for the case's operand needs while keeping the helper's data-register-to-data-register form. For an inert helper, copy between two different registers, preferably both unused by the target: [ADD.W absolute long](../../../benchmarks/m68k/add/add_w_absolute_long/program.s) uses `MOVE.L D3,D4` while its target uses D2. Never use a self-copy such as `MOVE.L D7,D7`. A helper may read a target register when the copy cannot change the intended path, as in the postincrement example above. Verify that the full-width copy and its condition codes cannot change the intended target path. For PC-relative targets that read the preceding helper opcode as data, match the initial data word to the assembled `MOVE.L` opcode and inspect every target's effective address. Final condition-code values are irrelevant to this benchmark; consider flags only when they select different executed work or timing. Keep any additional setup or control instructions required by the measured path outside this four-target sequence where possible, and account for all executed helpers.
   When a target already needs a register or status restoration after it, use that instruction as the helper without an additional inert `MOVE.L`. Do not use `LEA` as a setup or interleaving helper.
2. Keep only `program.s` and `case.json` in the case directory. Put the target program and addressable operand data in the assembly image. For RAM operands outside that image, declare a `fixed_words` memory region with an address and values, but no label. For an exception vector, use a `label_address` region with the vector name and a handler label from `program.s`; do not hardcode the assembled address as two words. The runner disables the low-memory ROM overlay and restores these regions before each run. Declare image origin and target primary opcode in `case.json`. Initialize only registers whose starting values the program uses; omit registers that the program never references or overwrites before reading. Check each `initial_registers` entry against the executed instructions, including address and index registers. The CPU's built-in defaults are SR `$2700` and zeroed registers. Put every case-specific initial register value in `case.json` under `initial_registers`, including `ssp` or `usp` when A7 is used. Put a non-default status register in `initial_sr`. The shared runner must not invent, calculate, or hardcode register initial values; it may only apply values read from the case configuration. `stack_reserve_bytes` reserves memory and never determines a register value. Check the configured stack pointer, active bank, access direction, width, and full access range against that reserve. Keep shared `instruction_count`, `instruction_limit`, `series`, and `target_series_ms` in `benchmarks/m68k/config.json`. Do not add a Rust runner to an instruction directory.
3. The shared `instruction_count` is currently 100,000 target instructions. Set `instructions_per_loop` to `4` for the four-target `rept` block; the runner substitutes one quarter of the shared target count as the source repetition count. Inspect the assembled target opcodes and verify that the program executes the declared number of targets. The runner uses this configured target count and observes total executed instructions and CPU clocks; it does not classify targets by opcode. Check assembled size, data use, and run duration. Size static operand data for the addresses and access widths actually used: a fixed `ADD.W` operand needs one word, while advancing address registers need enough data for every repetition. Do not copy an operand block with several words from another case without checking which words are read or written. This count is a starting value, not a requirement for every instruction. If a case cannot fit or needs a different count, make the configuration decision explicit; do not silently change the shared setting for all cases. Keep each timed run a complete execution of the assembled program.

`initial_registers` accepts D0-D7, A0-A6, `ssp`, and `usp`; configure the active A7 bank explicitly. Do not use an `a7` entry.

## Assemble and load

- Provision the pinned assembler with `tools/bootstrap/bootstrap.ps1 -Assembler`. Read its release and expected executable hash from `tools/bootstrap/assembler-manifest.json`; reject a missing or mismatched executable before assembly. Do not depend on a global assembler or an unsupported `--version` option.
- The current assembler does not accept a command-line symbol definition for the repetition count. Use the deliberate `{{instruction_count}}` marker and save the effective assembly source with the result. For generated operands, declare a memory region with `label`, expected `address`, and a typed `fill` in `case.json`; put `{{label}}` after that label in `program.s`. The shared `random_words` fill generates deterministic `dc.w` data from a fixed runner seed and the configured word count. Do not put a seed in case JSON. Static assembly data can stay directly in `program.s`.
- Assemble once outside measurement. Load the **entire binary image** at the case's configured Fast RAM origin, including code and data. Derive the entry from the assembler's `entry` symbol. Put `dc.b "M68K_END_MARKER!"` after the instruction block. The runner finds the unique marker in the binary and derives the program boundary from its address; bytes after the marker remain in the image. Use `endr` to close `rept`; the pinned assembler repeats a directive following `endm`.
- Check that the image fits in the installed Fast RAM without entering any configured stack reserve. Review operand access bounds and alignment in the assembly program. Do not infer code length from data length, target count, or a fixed two-byte opcode size. Preserve guest big-endian data when generating words and longs.

## Execute and measure

- Build explicit initial CPU and `PhysicalMemory` state, set the entry PC, and retain a clean copy for every run. Keep register and memory initialization case-specific. Loading or restoring the assembled image may initialize writable operands; any additional state must also be restored before each run.
- Define a bounded completion condition for the program. The current runner stops when the instruction PC reaches the end marker's address, checks that execution stays before the marker, and enforces `instruction_limit`. A branch, exception, or stop case needs its own justified completion check. Do not execute the marker bytes as CPU instructions.
- Verify the assembled target sequence for each program. The runner trusts the configured target count, so an unintended helper or branch path can make the reported helper count misleading even when the total instruction count is stable.
- Review the assembled source and image for the intended instruction workload. Use the first timed program to observe target, helper, total instruction, and CPU clock counts. Confirm that each conditional or exceptional case actually takes its named path, including its branch destination or exception vector and recovery path. Timed runs must keep the same instruction and clock counts. Instruction correctness belongs to the existing CPU tests; do not add opcode-specific expected-result calculations to this benchmark runner.

## Measure and report

- Initialize or restore CPU and memory outside the timer. Time complete executions through `Cpu::step_instruction`; include any guest setup or control instructions in the measured program. Derive the helper count from observed total instructions minus configured targets; divide the whole duration by target count for nanoseconds per target. Repeat whole programs until each series reaches `target_series_ms`, then run the configured number of series (three by default). Do not stop in the middle of a program to meet the duration target.
- Report the assembler release and hash, source and image hashes, origin and entry, image size, effective case and measurement settings, target and total instruction counts, CPU clocks, runs per series, elapsed time, host load, and spread. Describe nanoseconds per target as the host cost of this **whole workload**. Do not label it isolated opcode latency.
- Run the case through `python tools/verification/verify.py runner bench case <family>/<case-id>`. Keep instruction-specific setup declarative in JSON and extend the shared runner only when a new initialization or fill strategy requires it.

## Check the result

Run a small assembly probe for symbol placement and instruction encoding, especially with `rept`, branches, or mixed data and code. Run the complete case and inspect the effective source, binary image, symbol addresses, execution counts, and JSON report under `benchmarks/results/`. Run focused Rust formatting and Clippy checks plus repository checks relevant to the changed files. Keep generated source, binaries, and symbols under `.agent/tmp/benchmarks/`; leave the incompatible retained baseline unchanged unless its replacement is explicitly approved.
