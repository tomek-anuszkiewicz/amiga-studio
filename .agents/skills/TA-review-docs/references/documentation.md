# Specifications, documentation and governance

Apply the shared [documentation criteria](../../../references/documentation-criteria.md)
and relevant instruction ownership/specification requirements. They include scoped
compliance selection, broader milestone obligations and document-value assessment;
using these criteria does not invoke another public skill.

Trace changed requirements into affected code/tests even without an implementation
diff. Assess required supplied audits and their coverage rather than repeating them.
Classify descriptive versus requirement-changing corrections and identify any other
lanes affected by changed criteria or evidence. For changed instructions, walk the
real invocation and inspect ownership, activation, stopping points and active callers.

Check metadata/link semantics and triggered diary/roadmap obligations. Preserve
hardware knowledge, independent requirements and unique rationale. Report needed
enrichment or repairs; do not edit documents, index content or launch other audits.

Check that the receiving-session explanation is concise, evidence-bounded and in
the user's language. Executable options need actual inputs and complete invocations;
missing prerequisites and criterion-change approval must remain visibly separate
from repair permission. Keep procedure ownership shared and future default authority
separate from a migration/trial coordinator's explicitly delegated decisions.

Check matrix rows/columns, condition meanings and the generated view against the
actual skills and readiness rules. Official recommendation limits must not be
documented as prohibitions on the user's direct choices. Keep the shared procedure
as the owner of matrix use instead of copying routing policy into every skill.
For added roles or skills, check the exact `TA-` identity, bounded operation,
owner and result contract. Check that the matrix's displayed effort agrees with
the runtime settings for the destination executor.
