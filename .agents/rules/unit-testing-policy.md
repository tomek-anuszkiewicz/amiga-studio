# Testing Policy

- Keep tests in the owning crate or tool's local `tests/` directory, such as `crates/<crate>/tests/` or `tools/bootstrap/html-to-markdown/tests/`. Do not create global test directories or place component-specific tests in the repository-root `tests/`. Cross-component tests belong to the component that owns their integration.
- Follow the owning crate's existing test layout; report uncovered behavior.
- Cover domain behavior and failure modes. Thin declarations and forwarders may rely on parent integration coverage; there is no minimum assertion count or arbitrary test-function quota.
- Reuse existing behavioral coverage; add tests only for a demonstrated gap.
- Maintain integration coverage when chips gate execution, transfer Chip RAM, signal peers, or compete for bus slots. Reuse existing production integration fixtures for coordination behavior. A synthetic bus isolates CPU behavior; it does not establish production bus or chipset scheduler correctness.
- Explain the expected result through a contract, specification, external reference or explicit invariant. A baseline generated by the implementation can establish stability or a relative property, such as invariance under waiting, but cannot independently establish absolute correctness.
- For defects, follow [defect resolution](structural-root-cause.md#defect-resolution). Keep shared setup in test helpers. Use existing host APIs or snapshots for observation; adding runtime API solely to simplify a test requires a demonstrated observation gap and an intentional interface. Remove test-only zombie runtime methods unless they intentionally expose host I/O or debugger controls.
- Distinguish behavioral tests, static architecture checks, performance measurements and diagnostic traces. Put source-inspection checks in verification tooling and measurements in benchmark targets. Keep generated reports in ignored artifact directories; report evidence only for the cases and properties actually checked.
- Verification has four tiers: isolated crate behavior, machine/debugger/GUI integration, CPU reference-vector verification, and whole-machine hardware captures. The capture execution entry point is currently unavailable. Every executed SingleStep vector must compare state, instruction clocks and timed bus transactions against its JSON reference. Sampling changes input count only; weaker verification modes and unverified-success skips are prohibited. Document harness limits through the [CPU verification specification](../../Obsidian/Amiga/Design/Verification/CPU%20SingleStepTests.md).
- When implementing a CPU execution path absent from the supplied SingleStep vectors, add a hand-written regression under `crates/cpu/tests/`. Establish its expectations from an independent reference or explicit hardware invariant, not the implementation being tested. Assert the resulting state and side effects, including unchanged state where relevant, and check cycle-exact behavior: total CPU clocks plus each bus access's CCK, address, direction, and transferred value where observable. Cover wait-state retries when the path introduces or changes bus behavior. Report the missing reference-vector coverage; passing neighboring vectors does not verify the absent path.
- Run relevant checks for the completed change; repeat only for changed inputs, failures or unresolved concerns. Run Python tool contracts only for affected owning inputs or shared dependencies with `python tools/verification/verify.py test python`, or select a directory explicitly for diagnosis. Before every authorized commit, run `python tools/verification/verify.py commit`; stage closure additionally runs `python tools/verification/verify.py milestone` once for the same snapshot. The commit profile selects Rust tests by changed packages and transitive consumers, with full verification for shared or unknown inputs; independent documentation and known Python tool changes skip Rust tests. It retains all quality gates and the existing Python contract policy, and excludes full SingleStep. Selection and fallback requirements belong to the [testing strategy](../../Obsidian/Amiga/Design/Verification/Testing%20Strategy%20and%20Quality%20Assurance.md#completion-entry-point). Milestone runs full SingleStep and the full language audit. Full standalone SingleStep runs are for explicit diagnosis or user requests. Use the [verification reference](../../tools/verification/README.md) for focused diagnostics and snapshot handling. Report actual checks and coverage gaps; changed test files alone prove no coverage.
- Run independent checks concurrently only when they do not share mutable inputs or one Cargo target directory. Do not edit the source snapshot while background checks validate it.

## Coverage During Development and Review

- For emulator production-code changes, measure coverage of the affected ordinary packages during implementation and inspect the unexecuted functions and source spans. Use the [coverage workflow](../../tools/verification/README.md#coverage-guided-testing); a percentage or a passing test run alone does not complete this review.
- Treat an uncovered reachable behavior in the changed code or its affected interactions as missing test protection. Add or extend behavioral tests within the task without asking for approval for each test. Assert independently expected results, state, side effects and timing where relevant; merely executing code is insufficient. Reuse integration tests when they protect the behavior.
- Check measurement scope before concluding that a test is missing. Tests outside the measured suites, other targets, conditional compilation and code absent from instrumentation require explicit evidence; do not report them as covered or silently exclude them. Full executable-code coverage is the goal, not proof of complete behavioral correctness.
- Resolve in-scope behavioral gaps before task completion and before an authorized commit. Review the final coverage evidence together with the assertions; do not substitute a global percentage threshold. Ask the user for unresolved expected behavior, specification conflicts or work beyond the authorized scope; preserve protected-verification approvals below.
- Report pre-existing gaps outside the task separately for a dedicated coverage audit. Do not hide them with coverage exclusions, allowlists, reduced measurement scope or tests without meaningful assertions. A separate whole-emulator audit does not run automatically for every edit or commit. Bootstrap conversion tooling retains its scope below.

## Protected Verification

- Architectural tests, their checker implementations and their policy data require explicit user approval before any addition, modification or deletion. This includes dependency permissions, limits, exceptions and enforcement scope, regardless of which file contains them. Even a stricter check or a mechanical refactor requires approval.
- A request to implement, refactor, fix tests or commit does not authorize changing these checks or approving new dependencies. Present the current constraint, the proposed diff, its rationale and its effect on accepted code; obtain approval for that concrete change before applying it. Approval covers only the presented change.
- When implementation conflicts with an architecture check, preserve the check and satisfy the existing constraint or request an architecture decision. Do not infer approval from edited manifests, matching design documentation, a passing check or another agent's review.
- Weakening any other existing test or required verification gate also requires explicit user approval before editing. This includes changing expected results or tolerances to accept different behavior, adding exceptions or comparison masks, removing or skipping assertions or cases, and reducing the enforced verification scope. Present the evidence, proposed diff and lost protection using the approval procedure above; a suspected incorrect or obsolete test does not authorize weakening it.
- Routine language corrections, reviewed vocabulary additions and justified exact-file literal entries have standing user authorization under [language policy](language-policy.md#resolving-findings). This exception does not authorize changes to scanner logic, authored scan coverage or other verification criteria.
- Ordinary test maintenance remains allowed when it preserves acceptance criteria and coverage, including symbol/import changes, fixture adaptation for an internal refactor, additional behavioral tests and stronger assertions. A specific user-approved contract change can authorize its corresponding test update; a generic implementation, test-repair or commit request cannot.
- Protected reference artifacts and comparison rules remain governed by [specification compliance](spec-compliance.md#reference-artifact-integrity).

## Bootstrap Converter Scope

Applies to `tools/bootstrap/conversion/`, `tools/bootstrap/pdf-to-markdown/`, `tools/bootstrap/html-to-markdown/` and `tools/bootstrap/book-to-markdown/`. Follow the [converter development instructions](../../tools/bootstrap/AGENTS.md#converter-development); emulator hardware and CPU verification requirements are unaffected.

- Keep existing technical tests for configuration, Codex transport, response/cache validity and restart/artifact preservation. These tests do not certify conversion quality. Run relevant existing checks for a concrete change; do not turn every edit into a full converter test campaign.
- Do not add tests by default or create coverage matrices, exhaustive stage/branch suites or automated conversion-quality evaluations. A new test must address a concrete technical defect within the requested task, rather than hypothetical coverage or the current pipeline's internal layout.
- Do not restore the removed asset/crop tests or introduce pixel-perfect crop assertions unless the user explicitly requests that testing scope. When redesign supersedes a mechanism, remove or adapt its obsolete tests with it; do not preserve old behavior solely to satisfy old tests.
- Fragment conversion runs occur at the user's request. The user selects the source fragment and evaluates the generated content; report execution failures and output locations. Do not independently choose samples, expand to the full book/crawl, compare models or tune quality. HTML runtime validation remains in place; PDF-STATE-1 removes PDF artifact, configuration and local response validation. PDF parsing, conversion IO and transport completion handling remain.
- Required repository per-commit checks still apply. Report their actual results separately from fragment conversion and user quality assessment.

The broader model is in [Testing Strategy and Quality Assurance](../../Obsidian/Amiga/Design/Verification/Testing%20Strategy%20and%20Quality%20Assurance.md).
