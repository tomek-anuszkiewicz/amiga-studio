# Testing Policy

- Rust tests live in `crates/<crate>/tests/`, never inline in `src/`. Test filenames start with `test_`; shared helpers live in `tests/common/mod.rs`. Some crates have no isolated suite; verify their behavior through the remaining integration suites and report the coverage limit.
- Cover domain behavior and failure modes. Thin declarations and forwarders may rely on parent integration coverage; there is no minimum assertion count or arbitrary test-function quota.
- Before adding a test, identify the behavior or failure mode it protects and check existing suites and authoritative vectors. Reuse or extend that protection; add a test for a demonstrated gap, not to mirror implementation structure or increase test counts. For mechanical moves, renames, formatting, or comments, run relevant existing tests instead of adding file-coupling assertions. Bootstrap converter exceptions follow below.
- Maintain integration coverage when chips gate execution, transfer Chip RAM, signal peers, or compete for bus slots. Reuse existing production integration fixtures for coordination behavior. A synthetic bus isolates CPU behavior; it does not establish production bus or chipset scheduler correctness.
- Explain the expected result through a contract, specification, external reference or explicit invariant. A baseline generated by the implementation can establish stability or a relative property, such as invariance under waiting, but cannot independently establish absolute correctness.
- For defects, follow [defect resolution](structural-root-cause.md#defect-resolution). Keep shared setup in test helpers. Use existing host APIs or snapshots for observation; adding runtime API solely to simplify a test requires a demonstrated observation gap and an intentional interface. Remove test-only zombie runtime methods unless they intentionally expose host I/O or debugger controls.
- Distinguish behavioral tests, static architecture checks, performance measurements and diagnostic traces. Put source-inspection checks in verification tooling and measurements in benchmark targets. Keep generated reports in ignored artifact directories; report evidence only for the cases and properties actually checked.
- Verification has four tiers: isolated crate behavior, machine/debugger/GUI integration, CPU silicon verification, and whole-machine hardware captures. The capture execution entry point is currently unavailable. Every executed SingleStep vector must compare state, instruction clocks and timed bus transactions against its JSON reference. Sampling changes input count only; weaker verification modes and unverified-success skips are prohibited. Document harness limits through the [CPU verification specification](../../Obsidian/Amiga/Design/Verification/CPU%20SingleStepTests.md).
- Ordinary task completion without a commit uses checks and tests relevant to a coherent change, not automatic checks after every edit. Repeat only when affected inputs change, a check fails, or a concern remains unresolved. Run Python tool contracts only for affected owning inputs or shared dependencies with `python tools/verification/verify.py test python`, or select a directory explicitly for diagnosis. Before every authorized commit, run `python tools/verification/verify.py commit`; stage closure additionally runs `python tools/verification/verify.py milestone` once for the same snapshot. The commit set runs all standard tests and all Python tool contracts but excludes full SingleStep. Milestone runs full SingleStep and the full language audit. Full standalone SingleStep runs are for explicit diagnosis or user requests. Use [test-runner](../skills/test-runner/SKILL.md) for focused diagnostics and snapshot handling. Report actual checks and coverage gaps; changed test files alone prove no coverage.
- Run independent checks concurrently only when they do not share mutable inputs or one Cargo target directory. Do not edit the source snapshot while background checks validate it.

## Bootstrap Converter Scope

Applies to `tools/bootstrap/conversion/`, `tools/bootstrap/pdf-to-markdown/` and `tools/bootstrap/html-to-markdown/`. Follow the [developer-led conversion workflow](../../tools/bootstrap/reference-conversion-contract.md#development-workflow); emulator hardware and CPU verification requirements are unaffected.

- Keep existing technical tests for configuration, Codex transport, response/cache validity and restart/artifact preservation. These tests do not certify conversion quality. Run relevant existing checks for a concrete change; do not turn every edit into a full converter test campaign.
- Do not add tests by default or create coverage matrices, exhaustive stage/branch suites or automated conversion-quality evaluations. A new test must address a concrete technical defect within the requested task, rather than hypothetical coverage or the current pipeline's internal layout.
- Do not restore the removed asset/crop tests or introduce pixel-perfect crop assertions unless the user explicitly requests that testing scope. When redesign supersedes a mechanism, remove or adapt its obsolete tests with it; do not preserve old behavior solely to satisfy old tests.
- Fragment conversion runs occur at the user's request. The user selects the source fragment and evaluates the generated content; report execution failures and output locations. Do not independently choose samples, expand to the full book/crawl, compare models or tune quality. Runtime input/output/schema validation remains part of converter execution.
- Required repository per-commit checks still apply. Report their actual results separately from fragment conversion and user quality assessment.

The broader model is in [Testing Strategy and Quality Assurance](../../Obsidian/Amiga/Design/Verification/Testing%20Strategy%20and%20Quality%20Assurance.md).
